## 7.1 诊断体系总则（三层诊断）

> **总则**：诊断必须**分层归属**——每一层有唯一载体、唯一错误码族与唯一退出码域。任何诊断不得跨层混用载体，否则 CI 无法在不解析自由文本的前提下作出确定性判定。

### 7.1.1 三层模型

| 层 | 名称 | 触发时机 | 载体 | 产物 | 错误码 / 警告族 | 退出码域 |
|---|---|---|---|---|---|---|
| `L1` | **编译期诊断** | `P1`–`P4`（`05 §1`） | `Vec<Diagnostic>`（stderr 文本 + 报告 `checks[].diagnostics[]`） | 结构化诊断流、`ast.json`、`logic_profile.json` | `E-PARSE-*`、`W1`–`W12` 对应 `E-BAD-SORT`…`E-GROUNDING-BUDGET`、`E-CYCLIC-DECL`、`E-CROSS-DOMAIN-REF`、`E-WAIVER-MALFORMED`、`E-UNVERIFIABLE`；警告 `W-SHADOW`、`W-UNUSED-ENTITY` | `L1` 阻断 = `3`（`COMPILE_ERROR`） |
| `L2` | **求解期诊断** | `P5`–`P7`（求解器调用、响应解析、交叉验证） | `SolverVerdict` + 原始 S-Expr（`sat` 模型 / `unsat` 核） | `BusinessCounterexample`、`RuleConflictSpan[]`、耗时与求解器元数据 | `E-SOLVER-MISSING`、`E-SOLVER-VERSION`、`E-LOGIC-UNSUPPORTED`、`E-XVALIDATE-MISMATCH`（`E-CROSSVAL-MISMATCH` 同义，以 `04 §11.2` 的 `E-XVALIDATE-MISMATCH` 为准）、`E-EMPTY-CARRIER`（求解期空核特例，见 §7.3.3） | 判定失败 = `1`；UNKNOWN = `2`；内部 = `4` |
| `L3` | **治理期诊断** | 报告装配、门禁、评审与豁免 | `report.json`（`IF-3`）、`report.sarif`、`.policylang/reviews/<proof_hash>.json` | `overall_status`、`proof_hash`/`attestation_hash`、评审记录、豁免链 | `E-REPORT-WRITE`（`E-REPORT-IO` 同义）、`W-WAIVER-EXPIRED`、`W-REVIEW-EXPIRED`、`W-REVIEW-STALE` | 落盘/内部 = `4`；`Waived` 贡献 `0` 但报告中可见 |

> **载体唯一性（架构约束）**：`L1` 只写 `diagnostics[]`，绝不写 `counterexample`/`conflicting_rules`；`L2` 只写 `counterexample`/`conflicting_rules`，绝不修改 `diagnostics[]`；`L3` 只写 `waivers[]`/`overall_status` 与哈希字段。三者的写入者分别为 `CR-3`/`CR-4`（`L1`）、`CR-6`（`L2`）、`CR-7`（`L3`）（`02 §2`）。

### 7.1.2 诊断记录规范形态

所有 `L1` 诊断以如下结构进入报告（有序数组，字段顺序固定）：`{ code, severity, message, span, fix_template }`。

| 字段 | 语义 | 约束 |
|---|---|---|
| `code` | 错误/警告码，取自 `04 §11` 全表 | 必填；`^[EW]-[A-Z0-9-]+$` |
| `severity` | `error` / `warning` / `info` | 必填；`error` 且族属 `E-UNVERIFIABLE` 者退出码 `3` |
| `message` | 人类可读文案（**不参与任何哈希**） | 必填；允许本地化，禁止作为机读判定依据 |
| `span` | 源码行列跨度（`start` 含、`end` 不含） | 可为 `null`（如全局预算判定无单一规则归属） |
| `fix_template` | 修复模板 ID（`FIX-n`，见 §7.4） | 生产端**必须**填写；消费方按 §7.4 表复算渲染 |

> **纪律**：`message` 允许自然语言，但**任何自动化决策不得依赖 `message`**。机读判定只能使用 `code`、`severity`、`span`、`fix_template`、`status`、`verdict` 等**枚举化字段**。此约束使 CI 脚本无需 NLP 即可确定性地作出门禁决策。

## 7.2 反例模型还原（S-Expr → 业务实体视图）

> **目标**（`FR-7`，`TH-1-C2`）：把求解器返回的扁平标量赋值（如 `PL_Services_2_host_ip = (_ bv167772165 32)`）**唯一**还原为业务实体视图（`Services[3].host_ip = "10.0.1.5"`），并保证该还原是**确定性纯函数**，可离线复算。

### 7.2.1 实例索引 ↔ 业务标识映射规则

> **核心映射规则（本文冻结）**：
>
> 1. **内部索引（SMT 侧）**：`domain D` 的实例索引集为 `idx(D) = Fin N = {0, 1, …, N−1}`（`03 §3.2.4` 定义 3.2.2；`N = size(D) ≥ 1`，W3）。展平符号中的十进制数字即此内部索引：`PL_D_i_f`。
> 2. **业务显示编号（视图侧）**：实例**从 1 起编号**，写作 `D[1] … D[N]`。显示编号 `k = i + 1`，与内部索引 `i` 构成双射 `φ: Fin N → {1,…,N}, φ(i) = i+1`。
> 3. **业务主键（`@key` 标注）**：用户可在实体字段上以 `@key` 标注**业务主键**（例如 `@key id: Int [min: 1, max: 100]`）。若实体中恰有一个 `@key` 字段 `f_k`，则该实例的业务标识为 `key(D, i) = value(flat(D, i, f_k))`；其显示形为 `D[<key>]`（如 `Services[S-042]`）。
> 4. **未标注时的回退**：若实体**无** `@key` 字段，业务标识回退为显示编号 `D[k]`（`k = i+1`）。若存在**多个** `@key` 字段，则为 `E-BAD-SORT` 级别的声明冲突（编译期阻断，退出码 `3`）。

> **术语与文档一致性提示（重要）**：`03 §3.2.4`、`05 §8.2` 与 `02 §7 IF-3` 的示例按**内部索引（0 起）**书写，如 `Services[0]`。本文规定的**业务显示编号为 1 起**，即同一实例在 `03`/`05` 记作 `Services[0]`、在本视图记作 `Services[1]`（内部 `internal_index = 0`、`display_index = 1`）。报告**同时**携带两个字段（`internal_index`、`display_index`）以消除歧义；终端彩色诊断默认展示 `display_index`。此偏移在 `10 §10.2 AC-1` 的断言中显式校验。

**`@key` 标注的语义要求**：语法为在字段声明前加注解 `@key`（规范形态 `@key id: Int [min: 1, max: 100],`）；允许排序为 `Int` / `Str` / `Enum(E)` / `BV(n)`（含 `IPv4`/`IPv6`），**禁止** `Real`（有理数作主键不稳定）与 `Bool`（区分度不足）；每实体**至多一个** `@key`，违反即编译期阻断；声明 `@key` **不**自动注入 `unique(D, f_k)` 义务（`04 §3.5`：语义选择须显式声明，如需唯一性请显式写 `unique(D, id)`）；无 `@key` 时回退显示编号且**不报错**。该注解的**文法支持**为对 `04 §2` 与 `spec/grammar.pest` 的需求（登记为 `08` 的追溯项），本文仅冻结其**语义与展示规则**。（`@key` 业务主键标注为 `09 §9.5 OQ-7` 的待裁决候选，对应候选编号 `FR-21`，当前 `spec/grammar.pest` 与 `04 §2` 尚无产生式；未裁决前默认回退为实例索引形式 `D[i]`，**i 从 1 起**。）

### 7.2.2 排序格式化规范

格式化函数 `fmt : (Sort, Value) → String` 必须是**确定性纯函数**（同值同串）。

| 排序 `σ` | 业务显示格式 | 规范 | 反例（禁止） |
|---|---|---|---|
| `Int` | 十进制，负号前置 | `-42`、`0`、`65535` | `0042`（前导零）、`4.2e1` |
| `Real`（有理数） | 约分后：`den = 1` 时输出整数；否则 `num/den` | `1/2`、`3/4`、`-7` | `0.5`（浮点）、`2/4`（未约分） |
| `Bool` | `true` / `false` | `true` | `1` / `T` |
| `IPv4`（`BV(32)` 且族为 IPv4） | 点分十进制，四段无前导零 | `10.0.1.5` | `0x0A000105`、`010.0.1.5` |
| `IPv6`（`BV(128)`） | RFC 4291 压缩形式（省略最长全零段并以 `::` 表示） | `2001:db8::1` | 未压缩形式（非确定性：存在多种等价写法） |
| 其它 `BV(n)` | 十进制无符号 | `167772165` | `#xA000105`（宽度歧义，`03 §3.12.3`） |
| `Enum(E)` | 成员名（原样） | `Basic` | 整数编码 `1` |

> **`Real` 禁浮点（N-1，`03 §3.2.3`）**：`Real` 一律以 `num/den` 精确有理数格式化，**严禁**任何 IEEE-754 参与格式化或模型重放；否则跨平台 `proof_hash` 不可复算。

### 7.2.3 确定性 JSON 序列化（RFC 8785 / JCS）

报告的每一个字节都参与 `proof_hash` 的**上游构造**（§7.5），因此序列化必须是**规范形式**：

| 项 | 规范 | 依据 |
|---|---|---|
| 序列化算法 | **RFC 8785 JSON Canonicalization Scheme（JCS）** | `05 §8.3` |
| 对象成员序 | 按成员名的 **UTF-16 码元**序升序（JCS §3.2.3） | `05 §8.3` |
| 数字 | 最短往返表示（ECMAScript `Number::toString`），无 `+`、无前导零、无指数溢出 | JCS §3.2.2.3 |
| 字符串 | 按 JCS §3.2.2.2 转义（仅 `"`、`\`、U+0000–U+001F 需转义） | JCS §3.2.2.2 |
| 空白 | **无**任何多余空白（无缩进、无行尾空格） | JCS §3.1 |
| 编码 | UTF-8，**无** BOM | JCS §3.1 |
| 数组成员序 | **保序**（严禁排序）；数组语义为「有序列表」 | 本文硬性要求 |
| 字段序固定 | 由 `spec/report.schema.json` 的 `additionalProperties:false` + JCS 键序**双重**固定 | `IF-3` |

> **数组 vs 对象**：报告中的 `checks[]`、`entity_snapshots[]`、`fields[]`、`conflicting_rules[]`、`waivers[]`、`diagnostics[]` **一律为有序数组**，**严禁**用 JSON object 表示集合（object 的键序虽被 JCS 固定，但会引入「同一集合可被多键名表达」的歧义，并破坏 `spec/report.schema.json` 对元素形态的校验）。此规则与上游 v2.0 的 `HashMap<String, HashMap<String, String>>`（§5.1）**直接冲突**，以上游被否、本文为准。

### 7.2.4 还原算法（`decompile_model`）

```
ALG-7-A  decompile_model(M, naming) → BusinessCounterexample
输入   M       : S-Expr 模型块（( (PL_… v) … )）
       naming  : NamingContext —— scalar_symbol 的逆解析表（domain, index, field）→ Sort 与格式化器
输出   BusinessCounterexample

1  解析 S-Expr（05 §8.1），收集全部 (name, value) 原子对
2  对每个 name：
     (D, i, f) ← unflatten(name)                    // 逆解析（05 §8.2），失败则记为 unknown_symbol
     k        ← i + 1                               // 内部索引 → 业务显示编号（§7.2.1）
     snapshot[D] ← snapshot[D] ∪ { f ↦ fmt(sort(f), value) }
3  对每个域 D：按 i 升序聚合 snapshot，输出 entity_snapshots[]（有序数组），
     每项含 domain / entity / internal_index=i / display_index=i+1 /
     primary_key（@key 存在则填 {field, value}，否则 null）/ fields[]（按实体字段声明序）
4  globals[]：按变量声明序输出 { name, sort, value }
5  summary 由 L2 归因器填充（规则名 + 冲突点），非自由文本（§7.4）
```

> **不动点性质（`TH-1-C2` 推论）**：`unflatten` 是 `scalar_symbol` 的**左逆**（`scalar_symbol` 单射，`03 §3.2.4`），故对任一模型，`decompile_model` 的输出**唯一**；对同一 `sat` 判定与同一 `prop_hash`，两次运行的 `BusinessCounterexample` 逐字节相等。

> **`@key` 依赖提示**：`ALG-7-A` 第 3 步的 `primary_key` 字段依赖 `@key` 标注。（`@key` 业务主键标注为 `09 §9.5 OQ-7` 的待裁决候选，对应候选编号 `FR-21`，当前 `spec/grammar.pest` 与 `04 §2` 尚无产生式；未裁决前默认回退为实例索引形式 `D[i]`，**i 从 1 起**。）

## 7.3 冲突核归因（Unsat Core → 规则名与源码跨度）

> **目标**（`FR-7`，`TH-7 (i)`）：当 `consistency` 目标 `unsat` 时，把 `(get-unsat-core)` 返回的 `:named` 断言子集**归因**到 DSL 规则名与源码行列跨度。归因必须**最小化**，且对 `Bnd(S)` 引入的空核有专门处置。

### 7.3.1 核的非最小性与最小化

- `(get-unsat-core)` 返回的是**不可满足的 `:named` 断言子集**，**不保证最小**（`00 §0.3.1`「冲突核」定义）。
- 最小化采用 **deletion-based** 算法：逐一移除 `:named` 断言并重查 `UNSAT`，未被移除者可删去；复杂度 `O(A)` 次求解（`A` = 断言数），受独立预算约束（`03 §3.10.4`、`06 §6.9`）。
- **仅**当 `--minimize-core` 开启时执行最小化；**默认关闭**（大 `A` 时核心最小化会成为耗时主因，`03 §3.10.4`）。报告字段 `core_minimized` 记录是否已最小化。
- **`Bnd(S)` 不参与核**（`DD-3.1`，`03 §3.2.6`）：边界断言不带 `:named`，故建模假设不污染核。

```
ALG-7-B  minimize_core(Q, core, budget) → MinimalCore
输入  Q      : SMT-LIB2 查询文本（含 :named）
      core   : 求解器返回的核（有序符号列表）
      budget : 最大重查次数（默认 A，受 --core-budget 约束）
输出  最小核 core*（子集，保序），满足：删去任一元素即 SAT

core* ← core
for a in order(core):                                  // 前序遍历顺序（DET）
    if 重查次数 ≥ budget: break                        // 达预算即返回当前 core*
    if UNSAT(Q \ {a}):  core* ← core* \ {a}
return core*
```

### 7.3.2 归因到规则名与源码跨度

核中的符号形如 `Rule_<name>`（`05 §7.2`）。归因流程：

1. 取 `SmtQuery.named_map`（`:named` 标签 → `Span`，`05 §7.2`）做**单射**映射；
2. 每个核符号映射为一个 `RuleConflictSpan`，字段为 `rule_name` + `start_line` / `start_col` / `end_line` / `end_col`（**四行列**，修正上游 v2.0 仅有 `rule_name + line` 的粗粒度，见 `09 §9.2`）；
3. 输出数组按 `start_line` 升序、`start_col` 升序**保序**；
4. 若某核符号无法在 `named_map` 中命中（理论上不可能，`named_map` 由 `P6` 完整生成），记 `E-INTERNAL` 并回退为原始符号列表。

```json
{
  "check_name": "ServiceDeploymentPolicy::consistency",
  "target_type": "consistency", "status": "Fail", "verdict": "unsat",
  "conflicting_rules": [
    { "rule_name": "HighPort", "start_line": 30, "start_col": 5, "end_line": 31, "end_col": 48 },
    { "rule_name": "LowPort",  "start_line": 33, "start_col": 5, "end_line": 34, "end_col": 46 }
  ],
  "counterexample": null, "core_minimized": true
}
```

### 7.3.3 空核特例：`E-EMPTY-CARRIER`

> **判定条件**：查询 `UNSAT` 但 `(get-unsat-core)` 返回**空核**。数学意义：不可满足性**完全由建模假设 `Bnd(S)` 单独造成**，与任何 `:named` 规则无关（`03 §3.2.6 DD-3.1`）。

| 目标类型 | `unsat` 的朴素含义 | 空核时的**正确处置** |
|---|---|---|
| `consistency` | `Fail` | **不报 `Fail`**：报 `Error` + `E-EMPTY-CARRIER`（退出码 `3`）——冲突源于建模假设而非规则 |
| `invariant` / `refines` / `completeness` / `mutex` / `safety` | `Pass` | **严禁**记 `Pass`：报 `Error` + `E-EMPTY-CARRIER`（退出码 `3`）——否则会产出**假证明**（`Bnd` 不可满足使 `R_P ⟹ I` 空洞成立） |

> **安全论证**：对 `unsat = PASS` 的五类目标，若 `Bnd(S)` 自身不可满足，则 `M = ∅`，于是 `∀m ∈ M. π(m)` **空洞为真**——这是典型的**假证明（unsound PASS）**。因此空核**必须**降级为 `Error`，绝不产生 `Pass`。此机制与 `TH-7 (iii)` 的诚实阻断哲学一致，并构成 `INV-L3`（`01 §3.3`）在治理层的第二道闸门。
>
> **实践提示**：`Bnd(S)` 不可满足通常已被 `W3`（`E-EMPTY-CARRIER`）在编译期拦截。求解期空核多见于 **Enum 成员闭包与 `unique` 的交互**或**多域同符号名的边界叠加**等组合情形，此时 `L1` 静态检查无法预见，必须由本节的运行时守卫兜底。

## 7.4 修复建议生成（规则化、表驱动、可复算）

> **硬性纪律**：修复建议**严禁自由文本**。建议一律由 `verdict × target_type × 反例特征 → 模板 ID` 的**有限映射表**生成；模板为固定字符串，仅允许**确定性占位符替换**。由此，建议是反例模型的**纯函数**，可离线复算，不破坏 `proof_hash` 的可复算性（§7.5）。

### 7.4.1 反例特征提取（确定性）

`feature(M)` 为对反例模型 `M` 的**确定性布尔判定**，取值集合有限：

| 特征名 | 判定条件（对反例模型） |
|---|---|
| `SameHostPortConflict` | `∃ i≠j: host_ip_i = host_ip_j ∧ port_i = port_j`（`NoPortConflict` 类） |
| `DbInstanceDivergence` | `∃ i≠j: uses_db_i ∧ uses_db_j ∧ (db_host_i ≠ db_host_j ∨ db_port_i ≠ db_port_j)` |
| `OutOfSubnet` | `¬in_cidr(host_ip_i, net)`（不变量被违反的实例） |
| `ConflictingBoundPair` | 核含两条规则 `A ∧ B`，其常量上下界互斥（如 `port > 8000` 与 `port < 5000`） |
| `RangeWidened` | `refines`：反例落在 `[old_lo, old_hi] ∖ [new_lo, new_hi]` 的边界值 |
| `UncoveredRegion` | `completeness`：反例落在 `[lo..hi]` 的分支缝隙，满足 `⋀ ¬B_i` |
| `MutexOverlap` | `mutex`：反例同时满足 `B_A ∧ B_B` |
| `DenominatorZero` | `safety`：反例使某 `b_j = 0` |
| `BoundaryValue` | 反例中某变量取值等于其范围下界或上界 |
| `Timeout` | `verdict = unknown` 且原因为 `timeout` |
| `UnknownRiskLogic` | `verdict = unknown` 且逻辑档位为 `UNKNOWN_RISK`（`TH-3a`/`DD-3.2`） |
| `EmptyCore` | `unsat` 且核为空（§7.3.3） |
| `NonlinearConstruct` | `L1` 命中 `E-NONLINEAR` |
| `GroundingBudgetExceeded` | `L1` 命中 `E-GROUNDING-BUDGET` |
| `SolverUnavailable` | `L2` 命中 `E-SOLVER-MISSING` / `E-SOLVER-VERSION` |
| `CrossvalMismatch` | `L2` 命中 `E-XVALIDATE-MISMATCH` |

### 7.4.2 建议模板映射表（`FIX-1` … `FIX-16`）

| 模板 ID | `verdict` | `target_type` | 反例特征 | 建议模板（占位符 `{…}` 由特征值确定性填充） |
|---|---|---|---|---|
| `FIX-1` | `sat` | `invariant` | `SameHostPortConflict` | 将 `{D}[{j}].port`（当前 `{port_j}`）改为不等于 `{D}[{i}].port`（`{port_i}`）；或为 `{D}[{j}]` 指定不同 `host_ip` |
| `FIX-2` | `sat` | `invariant` | `DbInstanceDivergence` | 令 `{D}[{j}].db_host = {db_host_i}` 且 `{D}[{j}].db_port = {db_port_i}`；或将 `{D}[{j}].uses_db` 置为 `false` |
| `FIX-3` | `sat` | `invariant` | `OutOfSubnet` | 将 `{D}[{i}].host_ip`（当前 `{ip}`）调整至网段 `{net}` 内 |
| `FIX-4` | `unsat` | `consistency` | `ConflictingBoundPair` | 规则 `{rule_A}`（{span_A}）与 `{rule_B}`（{span_B}）的上下界互斥；放宽其一或将交集区间纳入合法域 |
| `FIX-5` | `sat` | `refines` | `RangeWidened` | 新策略放行了 `{D}[{i}].{field} = {value}`（旧策略不允许）；收紧新策略上界至 `{old_hi}` |
| `FIX-6` | `sat` | `completeness` | `UncoveredRegion` | 输入区间 `[{lo}, {hi}]` 无分支覆盖；补充分支或扩大相邻分支边界 |
| `FIX-7` | `sat` | `mutex` | `MutexOverlap` | 分支 `{B_A}` 与 `{B_B}` 同时命中（模型见附）；收紧二者边界使其不相交 |
| `FIX-8` | `sat` | `safety` | `DenominatorZero` | 策略 `{P}` 的分母 `{b_j}` 可为 `0`（模型给出 `{b_j} = 0`）；为 `{b_j}` 增设前置守卫或改用受限于 `[min ≥ 1]` 的载体 |
| `FIX-9` | `unknown` | 任意 | `Timeout` | 求解在 `{timeout_ms} ms` 内未决；降低展开规模（`size` 或改用 `distinct`）或提高 `--timeout` 后重试 |
| `FIX-10` | `unknown` | 任意 | `UnknownRiskLogic` | 逻辑档位 `{logic}` 经能力探测标记 `UNKNOWN_RISK`；仅接受 `UnknownReviewRequired`，请转人工评审 |
| `FIX-11` | `unknown` | 任意 | `BoundaryValue` | 反例贴边于 `{var} ∈ [{lo}, {hi}]`；若为数值不稳定导致 UNKNOWN，请显式收窄区间 |
| `FIX-12` | `unsat` | 任意 | `EmptyCore` | 建模假设 `Bnd(S)` 自身不可满足（`E-EMPTY-CARRIER`）；检查实体范围与 `Enum` 成员闭包的一致性 |
| `FIX-13` | `none` | 任意 | `NonlinearConstruct` | 非线性构造（`{op}`）；将除数固化为常量，或改用 `distinct` 分段枚举（`03 §3.11.4`） |
| `FIX-14` | `none` | 任意 | `GroundingBudgetExceeded` | 展开规模 `{G}` 超预算 `{G_max}`；将 `{D}.size` 由 `{N}` 降至 `≤ {N_suggest}` 或改用 `distinct` |
| `FIX-15` | `none` | 任意 | `SolverUnavailable` | 求解器 `{solver}` 缺失或版本不符（`E-SOLVER-MISSING`/`E-SOLVER-VERSION`）；按 `policylang.lock` 安装并对齐版本 |
| `FIX-16` | `none` | 任意 | `CrossvalMismatch` | 交叉验证不一致（`E-XVALIDATE-MISMATCH`）；禁用并上报该后端，保留参考求值器结论 |

> **完备性论证（可复算）**：`feature(M)` 为确定性判定（§7.4.1），映射表为**有限全函数**（对每个出现的 `(verdict, target_type, feature)` 组合皆有唯一行）。因此 `suggestion = TABLE[verdict, target_type, feature(M)]` 是反例模型的纯函数；对同一 `M`（或同一 `proof_hash`），两次运行产生**逐字节相同**的 `remediation.template_id` 与 `remediation.rendered`。

### 7.4.3 渲染与报告字段

建议以 `check.verdict_feature`（特征名，§7.4.1 枚举）与 `check.remediation = { template_id, rendered }` 两字段**置于 `checks[]` 元素层级**呈现（而非置于 `counterexample` 内）：`template_id` 为 `FIX-n` 枚举；`rendered` 为占位符替换后的确定性字符串，由特征值经 `fmt`（§7.2.2）确定性生成。二者均为必填且枚举封闭。置于检查层级的理由：修复建议对 **`sat`（反例）** 与 **`unsat`（冲突核）**、乃至 `unknown`/`Error` 三类皆适用（§7.4.2 覆盖全部 verdict），而 `counterexample` 仅对 `sat` 存在。

> **与 `proof_hash` 的关系**：建议文本**不**进入 `proof_hash` 的任何输入构造（§7.5.4）。理由：它是**从**判定结果**派生**的展示层内容；纳入将把「展示用占位符渲染」与「数学判定」耦合，反而削弱判定哈希的稳定性。但因其为纯函数，任何消费方可在持有 `proof_hash`、`spec`、`query`、`verdict` 的前提下**离线复算**建议。

## 7.5 审计报告规范

### 7.5.1 报告顶层结构

报告为单一 JSON 文档，`schema_version: "1.0"`（`00 §0.6`），与 `spec/report.schema.json` **严格一一对应**。顶层字段为：`schema_version`、`report_id`、`timestamp`、`overall_status`、`exit_code`、`logic_used`、`spec_hash`、`query_hash`、`proof_hash`、`attestation_hash`、`tool`、`attestation`、`checks[]`、`waivers[]`、`summary`。示例（省略 `checks[]`/`waivers[]` 明细）：

```json
{
  "schema_version": "1.0",
  "report_id": "rpt-20261014T170400Z-7c1a",
  "timestamp": "2026-10-14T17:04:00Z",
  "overall_status": "Fail",
  "exit_code": 1,
  "logic_used": "QF_SLIA",
  "spec_hash": "9f2c…（64 位十六进制）",
  "query_hash": "1b2c…",
  "proof_hash": "a1b2…",
  "attestation_hash": "f0e1…",
  "tool": { "name": "policylang", "version": "2.1.0" },
  "attestation": { "winner_solver": "cvc5", "solver_version": "1.2.0", "time_ms": 214,
                   "host": "ci-runner-07", "os": "linux", "arch": "x86_64" },
  "checks": [ /* 见 7.5.2 */ ],
  "waivers": [ /* 见 7.9 */ ],
  "summary": { "total": 1, "pass": 0, "fail": 1, "unknown": 0, "waived": 0, "error": 0 }
}
```

| 字段 | 语义 | 约束 | 是否进入 `proof_hash` |
|---|---|---|---|
| `schema_version` | 报告结构版本 | `const "1.0"` | 否 |
| `report_id` | 报告实例标识 | 非空；建议 `rpt-<UTC时间戳>-<短随机>` | 否 |
| `timestamp` | 生成时刻（UTC，RFC 3339） | 必填 | 否 |
| `overall_status` | 合并格 join 结果（`00 §0.4.2`） | 5 值枚举 | **是**（以 `verdict` 序列参与，见 §7.5.4） |
| `exit_code` | CLI 退出码 | `0`–`4`，由 `overall_status` 映射（`02 §6.3`） | 否 |
| `logic_used` | 实际使用的 SMT 逻辑档位 | 必填 | **是**（逻辑档位由 `T(φ)` 决定且随查询哈希固化） |
| `spec_hash` | 规范哈希（§7.5.3） | `^[0-9a-f]{64}$` | **是**（作为 `proof_hash` 的输入） |
| `query_hash` | 查询哈希（§7.5.3） | `^[0-9a-f]{64}$` | **是**（作为 `proof_hash` 的输入） |
| `proof_hash` | 溯源自证哈希（§7.5.4） | `^[0-9a-f]{64}$` | 自指（不参与自身） |
| `attestation_hash` | 运行证明哈希（§7.5.5） | `^[0-9a-f]{64}$` | 否（覆盖运行元数据） |
| `attestation.*` | 求解器、耗时、宿主 | `winner_solver`/`time_ms` 等 | **否**（关键：见 §7.5.6） |
| `checks[]` | 每目标检查结果（有序数组） | `minItems ≥ 1` | 间接（其 `verdict` 序列参与） |
| `waivers[]` | 生效/过期豁免（有序数组） | 可空 | 否 |
| `summary` | 状态计数 | 六值求和 = `total` | 否 |

### 7.5.2 `checks[]` 元素结构

```json
{
  "check_name": "ServiceDeploymentPolicy::invariant::PaymentSubnetIsolation",
  "target_type": "invariant",
  "status": "Fail",
  "verdict": "sat",
  "winning_solver": "cvc5",
  "time_ms": 214,
  "conflicting_rules": [],
  "counterexample": { /* 见 7.2.4：entity_snapshots[] / globals[] / summary / verdict_feature / remediation */ },
  "diagnostics": [],
  "core_minimized": false
}
```

| 字段 | 语义 | 约束 |
|---|---|---|
| `check_name` | 检查标识，形如 `<policy>::<target_type>::<symbol>` | 必填 |
| `target_type` | 量化枚举：`consistency` / `invariant` / `refines` / `completeness` / `mutex` / `safety` | 必填，枚举封闭（`04 §7`） |
| `status` | `GateStatus`（= `CheckStatus`，`00 §0.4.1`） | 必填，5 值枚举 |
| `verdict` | 求解器原始判定：`sat` / `unsat` / `unknown` / `none` | 必填；`none` 仅用于编译期 `Error` |
| `winning_solver` | 胜出求解器名 | 可 `null`（编译期 `Error`） |
| `time_ms` | 该目标求解耗时（毫秒） | `≥ 0` |
| `conflicting_rules[]` | 冲突核归因（§7.3.2） | 按目标类型条件出现（§7.5.2.1） |
| `counterexample` | 反例还原（§7.2） | 按目标类型条件出现 |
| `diagnostics[]` | 编译期诊断（§7.1.2） | 有序数组 |
| `core_minimized` | 是否已执行核最小化 | 布尔 |

**§7.5.2.1 条件出现约束（`oneOf` / `if-then`）**

| 条件 | 约束 |
|---|---|
| `target_type = consistency` 且 `status = Fail` | `conflicting_rules` 非空且 `counterexample = null` |
| `target_type ≠ consistency` 且 `status = Fail` | `counterexample ≠ null` 且 `conflicting_rules = []` |
| `status ∈ {Pass, UnknownReviewRequired, Waived}` | `counterexample = null` |
| 否则（`Error`） | 二者可空；由 `diagnostics[]` 承载归因 |

> 上述约束在 `spec/report.schema.json` 中以 `allOf` + `if`/`then` 表达，`counterexample` 与 `conflicting_rules` 的取值形态以 `oneOf`（具体对象 vs `null`）表达。

### 7.5.3 四哈希的精确定义与输入构造

下列定义**冻结**，实现不得偏离（`CR-7`，`02 §6.2`）。记 `SHA256(x)` 为 SHA-256 摘要，`‖` 为字节串连接，`JCS(x)` 为 §7.2.3 的规范序列化，`canon_src(·)` 为源码规范化（下定义）。

```
canon_src(text) ≜ 去 BOM → 行尾统一为 LF → 去除每行行尾空白 → 末尾保证恰一个 LF
canon_smt(text) ≜ 去 BOM → 行尾统一为 LF → 去除每行行尾空白 → 末尾保证恰一个 LF
```

**（1）`spec_hash` —— 规范哈希**

```
spec_hash ≜ hex(SHA256( canon_src(<.plm 源码 UTF-8>) ))      —— 单文件时为该文件；多文件时为按路径字典序的 canon_src 连接
```

**（2）`query_hash` —— 查询哈希**

```
query_hash ≜ hex(SHA256( canon_smt(<P6 生成的完整 SMT-LIB2 文本>) ))
```

> `query_hash` 可离线复算的前提是 `ground` 为**纯函数**：枚举顺序取 `Fin N` 元组字典序（`DET-1`）、`And`/`Or` 子项保序（`DET-2`）、声明按 `(domain,index,field)` 字典序发射（`05 §7.1`）。上述三点共同保证查询文本**逐字节稳定**（`03 §3.6.1`、`TH-10`）。

**（3）`proof_hash` —— 溯源自证哈希**

```
proof_hash ≜ hex( SHA256(
      SHA256(canon_src(spec))        ‖     // 32 字节原始摘要（非 hex）
      SHA256(canon_smt(query))       ‖     // 32 字节原始摘要（非 hex）
      canonical_verdict_utf8               // "sat" | "unsat" | "unknown"
   ) )
```

其中 `canonical_verdict_utf8` 是 `checks[]` 中有序序列的规范化编码，逐目标取 `verdict`：`join(checks.map(c ⇒ c.verdict), "\u001f")`（`\u001f` 为 US 分隔符，避免与任何判定词碰撞）。`proof_hash` **不**包含 `status`、`overall_status`、求解器名、耗时、宿主、时间戳——只有这样，「证明了什么」才与「谁在何时用什么证明了」解耦。

**（4）`attestation_hash` —— 运行证明哈希**

```
attestation_hash ≜ hex( SHA256(
      hex_to_bytes(proof_hash)        ‖     // 32 字节：绑定本次判定
      utf8(JCS(attestation_record))          // 运行元数据的规范序列化
   ) )

attestation_record ≜ {
   winner_solver, solver_version, time_ms, host, os, arch,
   solver_versions: [ { name, version, bin_sha256 } ],   // 取自 policylang.lock
   toolchain: { rustc, tokio, pest }
}
```

> `attestation_hash` 是**法证哈希**（`00 §0.3.2`）：它把「同一次判定」与「当次运行环境」绑定，用于审计追溯与复现争议；它**不**参与 `proof_hash`。

### 7.5.4 定理 `TH-10`（审计哈希确定性）

> **定理 `TH-10`（Audit Hash Determinism）**
> 设 `S` 为规范源码、`Q` 为 SMT-LIB2 查询、`v̄` 为判定序列。则
> 1. **确定性（可证）**：若 `canon_src(S)`、`canon_smt(Q)`、`v̄` 三者逐字节相同，则两次独立运行（不同机器、不同调度、不同求解器）产出的 `proof_hash` **逐字节相同**；
> 2. **可复算性（可证）**：任一方持有 `S` 与 `Q` 即可离线复算 `proof_hash = SHA256(SHA256(canon_src(S)) ‖ SHA256(canon_smt(Q)) ‖ v̄)`，无需重跑求解器；
> 3. **单射性（以碰撞抗性为假设）**：若 `proof_hash(S₁,Q₁,v̄₁) = proof_hash(S₂,Q₂,v̄₂)`，则在 SHA-256 抗碰撞假设下（可忽略概率）有 `(canon_src(S₁), canon_smt(Q₁), v̄₁) = (canon_src(S₂), canon_smt(Q₂), v̄₂)`。

**证明**

1. `canon_src` / `canon_smt` 是**确定性纯函数**（仅依赖输入字节，无时间/环境/随机源，`05 §8.3`）；`ground` 是纯函数（`DET-1`/`DET-2`，`03 §3.6.1`），故 `Q = P6(S)` 对固定 `S` 唯一；判定序列 `v̄` 由求解器给出并经 `TH-7` 解释；SHA-256 是确定性函数。三者复合仍为确定性纯函数，故 (1) 成立。
2. 由 (1) 的构造式，(2) 中公式即定义的直接展开；离线复算不需运行求解器，故 (2) 成立。
3. 由 SHA-256 的抗碰撞性（标准密码学假设），不同输入产生相同摘要的概率可忽略；故 (3) 在计算意义下成立。**注意**：这是一个**约化到密码学假设**的陈述，本文据实标注为假设而非定理内蕴性质。 ∎

> **推论 `TH-10-C1`（`AC-9` 的可验收性）** 同一 `S`、`Q`、`v̄` 下 `proof_hash` 100% 复现；`10 §10.2 AC-9` 直接以此推论为验收断言。`NFR-6`（审计完整性 100%）由此定理保障。

### 7.5.5 `TH-10` 的两个前提（诚实边界）

| 前提 | 内容 | 违反后果 |
|---|---|---|
| `P-a` | `ground` 为纯函数（`DET-1` 字典序、`DET-2` 保序、声明字典序发射） | `query_hash` 不可复算；必须由 `05 §11.4` 的差分测试守住 |
| `P-b` | `Real` 一律 `num/den`，**严禁** IEEE-754 参与（`03 §3.2.3 N-1`） | 跨平台格式化漂移；`spec_hash` 与模型重放失稳 |

### 7.5.6 为何 `winner_solver` 与耗时**不得**进入 `proof_hash`

> **这是本规范最容易被误实现的一处设计，故单独论证。**

| 论点 | 论证 |
|---|---|
| **A. 语义无关性** | `proof_hash` 要回答的问题是「**证明了什么**」，而非「**谁、在何时、以多快证明了它**」。求解器名与耗时属于**执行属性**（attestation），与命题 `π(V)` 的成立与否无关。若纳入，则同一规范在 Z3 与 CVC5 上会得到**不同**的 `proof_hash`，破坏「判定即事实」的可移植性。 |
| **B. 非确定性** | 首胜即止（`FR-8`）下胜出者**依赖调度与时序**：同一查询在某次运行由 CVC5 首先返回、另一次由 Z3 首先返回（`06 §6.6`）。耗时更是逐次波动。纳入非确定量会使 `proof_hash` **不可复算**，直接违反 `TH-10 (1)` 与 `NFR-6`。 |
| **C. 跨平台复算** | 宿主信息（CPU 主频、负载、OS）跨机器不同；纳入将导致 CI 与本地复算不一致，使 `AC-9` 无法通过。 |
| **D. 审计需求已被满足** | 「谁在何时以多快证明」的法证需求由 `attestation_hash`（§7.5.3(4)）**完整覆盖**：它以 `proof_hash` 为前缀，将判定与运行环境绑定，且可独立复算。故信息**无损失**，只是分层。 |
| **E. 最小特权哈希** | 拆分两种哈希使「数学事实」与「运行事实」具有**不同的信任边界**：前者可被任一方离线验证，后者只能在持有运行元数据时验证。混合会迫使所有复算方也持有运行元数据，降低可审计性。 |

> **规范化表述**：`proof_hash` 的输入构造**恰为** `(canon_src(S), canon_smt(Q), v̄)` 三元组；`winner_solver`、`time_ms`、`host`、`os`、`arch`、`solver_version`、`timestamp` **一律不进入**。它们仅进入 `attestation_hash` 与报告展示字段。

## 7.6 策略即代码与版本演进

### 7.6.1 Git 工作流

| 环节 | 规范 |
|---|---|
| 存储 | `.plm` 策略、`policylang.toml`（`IF-4`）、`policylang.lock`（`IF-5`）**全部**纳入 Git |
| 分支模型 | `main` 受保护；特性分支 `policy/<name>`；策略变更**必须**走 PR |
| 必需状态检查 | PR 必须通过 `policylang-gate`（§7.7）且 `overall_status ∈ {Pass, Waived}` |
| 提交粒度 | 一次提交对应一个**语义内聚**的策略变更；跨策略的**语义收敛**（`refines`）在 PR 描述中显式声明 |
| 不可变证据 | 门禁产出的 `report.json` 作为 PR 构建工件归档；`proof_hash` 记入 PR 元数据 |
| 变更即触发 | 仅当 `policies/**/*.plm` 或锁文件变更时触发门禁（§7.7 的 `paths` 过滤） |

### 7.6.2 `refines` 在 PR 阶段的用法（`FR-11`）

`refines` 是**语义收敛**（`P_new ⟹ P_old`）的机械化判据（`00 §0.3.2`），其双查询编码见 `06 §6.3.3`。PR 阶段规范用法：

```
# 新旧策略并存于同一规范文件
verify NewPolicy refines OldPolicy
```

| 门禁语义 | 判定 | 处置 |
|---|---|---|
| `Pass`（`unsat`） | 新策略**严格收敛或等价**，无暴露面扩大 | 允许合并 |
| `Fail`（`sat`） | 新策略**放行了**旧策略不允许的配置 | **阻断合并**；PR 评论展示被放行边界反例（`FIX-5`） |
| `UnknownReviewRequired` | 无法在预算内判定 | 转人工评审（§7.8） |

> **PR 规范**：任何**扩大**暴露面的策略变更，必须在 PR 描述中以显式 `refines` 目标声明，并附反例（若 `Fail`）或收敛证据（若 `Pass`）。禁止「静默放宽」。

### 7.6.3 Subsumption 矩阵（策略包含性）

设 `P_a`、`P_b` 为两策略，`refines(a,b)` 记为 `a ⊆ b`（`R_a ⟹ R_b`）。包含性关系矩阵（两个方向的 `refines` 判定结果 → 关系）：

| `P_a ⟹ P_b` | `P_b ⟹ P_a` | 关系 | 语义 | 门禁处置 |
|---|---|---|---|---|
| `Pass` | `Pass` | **等价（Equivalent）** | `R_a ≡ R_b` | 允许（可建议合并去重） |
| `Pass` | `Fail` | **严格更严（Strictly Stricter）** | `R_a ⟹ R_b` 且 `R_a ≢ R_b` | 允许（收敛） |
| `Fail` | `Pass` | **严格更宽（Strictly Broader）** | 扩大暴露面 | **阻断**（需显式评审） |
| `Fail` | `Fail` | **不可比（Incomparable）** | 互不蕴含 | **阻断**（需人工判定方向） |
| `Fail`（`unsat` 空核） | `Fail` | **不相交（Disjoint）** | 由 `E-EMPTY-CARRIER`/空核判定（§7.3.3） | **阻断**（建模假设问题） |

> **矩阵的确定性**：`refines` 每格取值仅依赖两个方向的 `unsat`/`sat`/`unknown` 判定（`06 §6.3.3` 的双查询四态），故矩阵是判定结果的纯函数。

### 7.6.4 基线对比 `--baseline`

```
policylang verify policies/*.plm --baseline .policylang/baseline/report.json
```

| 行为 | 规范 |
|---|---|
| 基线载体 | 上一次通过门禁的 `report.json`（按 `spec_hash` 归档于 `.policylang/baseline/`） |
| 对比维度 | ① `checks[]` 的 `status` 迁移（`Pass→Fail` 为**回归**，`Fail→Pass` 为**改进**）；② `proof_hash` 变化（判定事实变更）；③ `spec_hash` 变化（源码变更） |
| 回归判定 | 任一目标 `status` 由 `Pass`/`Waived` 退化为 `Fail`/`UnknownReviewRequired`/`Error` ⇒ **回归**，退出码取合并格最大者且门禁阻断 |
| 增删目标 | 新增目标按常规判定；删除目标记 `W-*` 提示（不得静默消失） |
| 与 `refines` 的关系 | `--baseline` 是**报告级**差分；`refines` 是**语义级**收敛。二者互补：前者发现「同目标判定退化」，后者发现「规则集语义漂移」 |

## 7.7 CI/CD 门禁集成（5 分支）

> **修正目标**：上游 v2.0 §5.2 的门禁脚本为 **3 分支**（`Pass` / `UnknownReviewRequired` / 其它 → `Fail`），会把 `overall_status = Error` 误判为 `Fail`（`09 §9.2 B-16`）。本节给出**5 分支**门禁，显式覆盖全部 `overall_status` 并把 `Error` 细分为 `3`（编译/守卫阻断）与 `4`（内部错误）。

### 7.7.1 退出码 ↔ 分支映射（唯一权威）

| `overall_status` | CLI 退出码 | 分支动作 | 依据 |
|---|---|---|---|
| `Pass` | `0` | 放行 | `00 §0.4.3` |
| `Waived` | `0` | 放行（报告中可见，需在审批流留痕） | `00 §0.4.1` |
| `Fail` | `1` | **阻断**；回写反例/冲突核诊断 | `FR-12` |
| `UnknownReviewRequired` | `2` | **阻断**；转人工评审（§7.8） | `FR-10` |
| `Error`（`E-UNVERIFIABLE` 家族 / 解析 / 合式性） | `3` | **阻断**（编译错误） | `02 §6.3` |
| `Error`（`E-SOLVER-*` / `E-XVALIDATE-MISMATCH` / `E-REPORT-WRITE` / `E-IO` / `E-INTERNAL`） | `4` | **阻断**（内部错误） | `02 §6.3` |

> **`Error` 的内部分派规则**（YAML 中 `jq` 实现）：读取 `checks[].diagnostics[].code`，凡**任一**码以 `E-SOLVER-` / `E-CROSSVAL` / `E-XVALIDATE` / `E-REPORT` / `E-IO` / `E-INTERNAL` 开头 ⇒ `4`，否则 ⇒ `3`。

### 7.7.2 GitHub Actions（完整可复制）

```yaml
# .github/workflows/policylang-gate.yml
name: Formal Policy Verification Gate

on:
  pull_request:
    paths:
      - "policies/**/*.plm"
      - "policylang.lock"
      - "policylang.toml"
      - ".github/workflows/policylang-gate.yml"

permissions:
  contents: read
  pull-requests: write
  security-events: write

concurrency:
  group: policylang-gate-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  formal-verify:
    name: policylang verify (5-branch gate)
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    env:
      TIMEOUT_MS: "3000"
      MAX_GROUNDINGS: "1000000"
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Cache SMT solver binaries
        id: solver-cache
        uses: actions/cache@v4
        with:
          path: ~/.policylang/solvers
          key: solvers-${{ runner.os }}-${{ hashFiles('policylang.lock') }}

      - name: Install SMT solvers (cache miss only)
        if: steps.solver-cache.outputs.cache-hit != 'true'
        run: |
          set -euo pipefail
          sudo apt-get update
          sudo apt-get install -y --no-install-recommends z3 cvc5
          mkdir -p "$HOME/.policylang/solvers"
          cp "$(command -v z3)"   "$HOME/.policylang/solvers/z3"
          cp "$(command -v cvc5)" "$HOME/.policylang/solvers/cvc5"
          # Bitwuzla：按 policylang.lock 下载预编译包并校验 SHA-256
          echo "Bitwuzla installation is performed per policylang.lock"

      - name: Put cached solvers on PATH
        run: echo "$HOME/.policylang/solvers" >> "$GITHUB_PATH"

      - name: Build policylang CLI
        run: cargo build --release --locked -p policylang-cli

      - name: Run formal verification (capture exit code)
        id: verify
        continue-on-error: true
        run: |
          set +e
          ./target/release/policylang verify \
            policies/*.plm \
            --timeout "${TIMEOUT_MS}ms" \
            --max-groundings "${MAX_GROUNDINGS}" \
            --minimize-core \
            --output report.json \
            --sarif report.sarif
          echo "verify_exit=$?" >> "$GITHUB_OUTPUT"

      - name: Enforce 5-branch gate (jq status determination)
        if: always()
        id: gate
        run: |
          set -euo pipefail
          jq -e '.schema_version == "1.0"' report.json > /dev/null
          jq -e '.checks | length >= 1' report.json > /dev/null
          jq -e '.overall_status | IN("Pass","Fail","UnknownReviewRequired","Waived","Error")' report.json > /dev/null
          STATUS="$(jq -r '.overall_status' report.json)"
          CODE=0
          case "$STATUS" in
            Pass|Waived)           CODE=0 ;;
            Fail)                  CODE=1 ;;
            UnknownReviewRequired) CODE=2 ;;
            Error)
              if jq -e '[.checks[].diagnostics[].code]
                        | any(startswith("E-SOLVER-") or startswith("E-CROSSVAL")
                          or startswith("E-XVALIDATE") or startswith("E-REPORT")
                          or startswith("E-IO") or startswith("E-INTERNAL"))' report.json > /dev/null; then
                CODE=4
              else
                CODE=3
              fi ;;
            *) CODE=4 ;;
          esac
          echo "overall_status=$STATUS" >> "$GITHUB_OUTPUT"
          echo "exit_code=$CODE"      >> "$GITHUB_OUTPUT"

      - name: Upload SARIF
        if: always()
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: report.sarif
          category: policylang

      - name: Upload audit artifacts
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: policylang-report
          path: |
            report.json
            report.sarif

      - name: Comment diagnostics on PR
        if: always() && github.event_name == 'pull_request'
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          set -euo pipefail
          STATUS="$(jq -r '.overall_status' report.json)"
          {
            echo "### PolicyLang 形式化门禁：\`${STATUS}\`"
            echo ""
            echo "| check | target_type | status | verdict | solver | time_ms |"
            echo "|---|---|---|---|---|---|"
            jq -r '.checks[] | "| \(.check_name) | \(.target_type) | \(.status) | \(.verdict) | \(.winning_solver // "-") | \(.time_ms) |"' report.json
            echo ""
            echo "<details><summary>反例与冲突核诊断（业务可读）</summary>"
            echo ""
            echo '```json'
            jq '[.checks[] | select(.status == "Fail") | {check_name, target_type, conflicting_rules, counterexample}]' report.json
            echo '```'
            echo ""
            echo "> 修复建议模板见 07 §7.4（`FIX-n`）；UNKNOWN 转人工评审见 07 §7.8。"
            echo "</details>"
          } > comment.md
          gh pr comment "${{ github.event.pull_request.number }}" --body-file comment.md

      - name: Fail the job with the mapped exit code
        if: always()
        run: |
          set -euo pipefail
          echo "overall_status=${{ steps.gate.outputs.overall_status }} 映射退出码=${{ steps.gate.outputs.exit_code }}"
          exit "${{ steps.gate.outputs.exit_code }}"
```

### 7.7.4 SARIF 输出规范（`FR-19`）

`policylang verify --sarif` 生成 SARIF 2.1.0 文档，映射规则：

| 报告字段 | SARIF 元素 | 映射规则 |
|---|---|---|
| `checks[].status = Fail` | `result.level = "error"` | 反例/冲突核 → `result.message.text`（业务可读摘要） |
| `checks[].status = Error` | `result.level = "error"` | 诊断码 → `result.ruleId` |
| `checks[].status = UnknownReviewRequired` | `result.level = "warning"` | 附 `properties.review_required = true` |
| `checks[].status = Waived` | `result.level = "note"` | 附 `properties.waiver = <waiver_name>` |
| `rule_conflict_span` / `span` | `result.locations[].physicalLocation.region` | `startLine`/`startColumn`/`endLine`/`endColumn`（**1 起**，与源码行列一致） |
| `tool.name` / `version` | `runs[].tool.driver` | `name` / `semanticVersion` |
| `proof_hash` | `runs[].properties.proof_hash` | 便于代码扫描平台回溯审计报告 |

> **SMT-LIB 位置语义**：SARIF 的列号约定为 1 起；本框架 `Span` 亦为 1 起（`05 §2.2`），故**无需偏移转换**。`end` 为**不含**端点，与 SARIF `region` 的 `endColumn`（不含）一致。

## 7.8 UNKNOWN 人工评审流（完整状态机）

> **原则**（`FR-10`，`G-8`，`TH-7 (iii)`）：`UnknownReviewRequired` **严禁**被视为 `Pass`；它必须在**有界时限内**经人工裁决，且全过程持久化、追加式留痕。

### 7.8.1 状态定义

`ReviewState` 枚举（持久化于 `.policylang/reviews/<proof_hash>.json` 的 `state` 字段）：

| 状态 | 语义 | 与 `CheckStatus` 的关系 |
|---|---|---|
| `Pending` | 评审已创建、待裁决（**初始态**，即 `UnknownReviewRequired` 的持久化表示） | 对应 `UnknownReviewRequired` |
| `Acknowledged` | 已确认该 UNKNOWN 为**已知且可接受**的不确定性，不视为通过；留给后续版本重验 | 仍为 `UnknownReviewRequired` |
| `WaivedByApproval` | 经审批人批准**限时豁免**（转入 §7.9 的 `Waived`） | 合并为 `Waived`（退出码 `0`，报告中可见） |
| `Superseded` | 该 UNKNOWN 因**规范变更**（新 `spec_hash`/`proof_hash`）而失效，由后继评审取代 | 该评审关闭；后继评审的判定为准 |
| `Escalated` | 超时或争议升级至架构委员会/更高层级 | 仍为 `UnknownReviewRequired`；门禁保持阻断 |

### 7.8.2 状态转移表

| 起始状态 | 事件 | 目标状态 | 触发条件 | 副作用 |
|---|---|---|---|---|
| `Pending` | `ack`（确认） | `Acknowledged` | 责任人确认已知信息 | 追加日志；门禁**仍阻断** |
| `Pending` | `approve_waiver`（批准豁免） | `WaivedByApproval` | 提供 `owner`/`approver`/`expires` | 生成 `Waiver`（§7.9）；`status` 合并为 `Waived` |
| `Pending` | `supersede`（规范变更） | `Superseded` | 新 `spec_hash` ≠ 旧值 | 关闭本评审；后继按新 `proof_hash` 重建 |
| `Pending` | `escalate`（升级） | `Escalated` | 责任人主动，或 `review.sla_days` 超时 | 追加日志；通知架构委员会 |
| `Acknowledged` | `approve_waiver` | `WaivedByApproval` | 同上 | 同上 |
| `Acknowledged` | `supersede` | `Superseded` | 规范变更 | 关闭 |
| `Acknowledged` | `escalate` | `Escalated` | SLA 超时或争议 | 升级 |
| `Escalated` | `approve_waiver` | `WaivedByApproval` | 委员会批准 | 生成 `Waiver` |
| `Escalated` | `supersede` | `Superseded` | 规范变更 | 关闭 |
| 任意终态（`WaivedByApproval`/`Superseded`） | `reopen` | `Pending` | `proof_hash` 复现且豁免过期 | 重新进入评审 |

> **不可达转移**：`Superseded → WaivedByApproval`、`WaivedByApproval → Acknowledged`（豁免一经批准只能通过过期回退 `Fail` 或 `reopen` 重入，不得降级为「确认」）。违反即 `E-INTERNAL`。

### 7.8.3 持久化路径与结构

### 7.8.4 追加式审计日志

路径：`.policylang/reviews/<proof_hash>.log.jsonl`（**JSON Lines**，**只追加、不修改、不删除**）。每行一个事件：

```jsonl
{"ts":"2026-10-14T17:04:00Z","actor":"ci","action":"create","from":null,"to":"Pending","proof_hash":"a1b2…","note":"all solvers returned unknown"}
{"ts":"2026-10-15T09:12:31Z","actor":"alice","action":"ack","from":"Pending","to":"Acknowledged","proof_hash":"a1b2…","note":"已知 QF_SLIA 自动机乘积膨胀"}
{"ts":"2026-10-16T11:40:02Z","actor":"bob","action":"escalate","from":"Acknowledged","to":"Escalated","proof_hash":"a1b2…","note":"需架构委员会裁决"}
```

| 字段 | 语义 | 约束 |
|---|---|---|
| `ts` | 事件时刻（UTC） | 必填；**单调不减**（追加式保证） |
| `actor` | 操作者（`ci` / 用户名 / 服务账号） | 必填 |
| `action` | 事件动作（枚举，见 §7.8.2） | 必填 |
| `from` / `to` | 迁移前后状态 | `create` 时 `from` 为 `null` |
| `proof_hash` | 绑定判定 | 必填；与文件名一致 |
| `note` | 人类备注（**不参与机读判定**） | 可选 |

### 7.8.5 时限与超时处置

| 项 | 规范 |
|---|---|
| 默认 SLA | `review.sla_days = 5`（工作日）；`deadline_at = created_at + SLA` |
| 超时判定 | 门禁运行时若发现某 `Pending`/`Acknowledged` 评审已过 `deadline_at` 且 `proof_hash` 仍复现 ⇒ 记 `W-REVIEW-EXPIRED`，**自动迁移** `→ Escalated`，并**保持退出码 `2`**（不因超时而放行） |
| 规范漂移 | 若评审的 `spec_hash` 与当前不符（源码已变）⇒ 记 `W-REVIEW-STALE`，自动迁移 `→ Superseded`，由新 `proof_hash` 重建评审 |
| 过期豁免 | `WaivedByApproval` 所依赖的 `Waiver` 过期 ⇒ 回退 `Fail`（§7.9.4），评审记 `reopen → Pending` |
| 阻断保证 | **任何** `Pending`/`Acknowledged`/`Escalated` 状态下，门禁**恒**阻断合并（退出码 `2`） |

> **不变量 `INV-REVIEW`**：`∀ 评审 r. (r.state ∈ {Pending, Acknowledged, Escalated}) ⟹ 门禁阻断`。此不变量使「UNKNOWN 永不坍塌为 PASS」在治理层获得机械化保障（`INV-L3`）。

## 7.9 豁免（Waiver）机制

> **定义**（`00 §0.3.2`）：豁免是带**责任人（`owner`）**、**审批人（`approver`）**与**到期日（`expires`）**的**限时例外**；过期即失效。豁免用于「失败但被显式、可审计地接受」的检查。

### 7.9.1 DSL 语法（以 `04 §3.7` 为准）

```policylang
waiver LegacyPortMigration {
    target:   NoPortConflict        // 被豁免的检查名（规则/不变量/目标）
    owner:    "alice"               // 责任人
    approver: "bob"                 // 审批人（须与 owner 不同）
    expires:  "2027-01-01"          // 到期日（ISO-8601，UTC 日）
    reason:   "legacy migration"    // 理由（人类可读，不参与机读判定）
}
```

| 键 | 必填 | 语义 | 约束 |
|---|---|---|---|
| `target` | 是 | 被豁免的检查名 | 须指向已声明检查名，否则 `E-UNKNOWN-TARGET` |
| `owner` | 是 | 责任人 | 非空 |
| `approver` | 是 | 审批人 | 非空；**须 ≠ `owner`**（四眼原则） |
| `expires` | 是 | 到期日 | ISO-8601 `YYYY-MM-DD`；非法即 `E-WAIVER-MALFORMED` |
| `reason` | 是 | 理由 | 非空（审计留痕） |

> 五键缺任一即 `E-WAIVER-MALFORMED`（`04 §3.7`、`04 §11.1`），编译期阻断，退出码 `3`。

### 7.9.2 生效条件

一个 `waiver w` 对检查 `c` **生效**当且仅当：

```
Effective(w, c) ≜ (w.target = c.check_name)
              ∧ (today < w.expires)                    // 未过期
              ∧ (w.owner ≠ w.approver)                 // 四眼原则
              ∧ (c.status = Fail)                      // 仅覆盖失败
```

### 7.9.3 `Waived` 状态与合并格的关系

- 生效豁免把检查的 `status` 由 `Fail` 改为 `Waived`。
- 合并格（`00 §0.4.2`）：`Error ⊐ Fail ⊐ UnknownReviewRequired ⊐ Waived ⊐ Pass`。`Waived` **严格低于** `UnknownReviewRequired`、**严格高于** `Pass`。
- 因此：`Waived` 与 `Pass` 双双贡献退出码 `0`（`00 §0.4.1`），但**报告中可见**；若同批检查中存在任一 `UnknownReviewRequired`/`Fail`/`Error`，则 `join` 取更高者，`Waived` 不掩盖更严重的状态。
- **与 `refines` 的交互**：`refines` 目标**默认不可豁免**（扩大暴露面属安全红线）；如需豁免，须在 PR 中显式声明并升级至架构委员会（`Escalated → WaivedByApproval`，§7.8.2）。
- **`require` 声明不可豁免**（`04 §3.6`）：`require` 语义为不可豁免的 `invariant`，其失败**永远**为 `Fail`，任何 `waiver` 对其无效。

### 7.9.4 生效与过期处置

| 情形 | 处置 | 退出码贡献 |
|---|---|---|
| 生效期内 `Fail` | `status := Waived`；`waivers[]` 记 `state = "Active"` | `0` |
| 到期后（`today ≥ expires`） | `status := Fail`（回退）；记 `W-WAIVER-EXPIRED`；`waivers[]` 记 `state = "Expired"` | `1` |
| `owner = approver` | 视为非法豁免：忽略并记 `W-WAIVER-MALFORMED`（警告，非阻断）；检查保持 `Fail` | `1` |
| `target` 不存在 | 编译期 `E-UNKNOWN-TARGET`（退出码 `3`） | `3` |
| 豁免链参与审计 | `waivers[]` 纳入报告；其**名称与状态**进入 `attestation_hash`（不进入 `proof_hash`，见 §7.5.6 论点 D） | — |

> **过期语义的形式化**：`W-WAIVER-EXPIRED` 触发后，`status` 由 `Waived` **单调回退**为 `Fail`（合并格上由低升高），故过期只会**收紧**门禁，绝不放松——这符合「诚实阻断」的单调性要求。

## 7.10 度量与看板

> **纪律**：度量指标（KPI）**不参与** `proof_hash`；它们从已归档的 `report.json` 时间序列聚合得出，可离线复算。

| ID | 指标 | 定义与口径 | 目标 / 告警线 | 数据来源 | 关联 |
|---|---|---|---|---|---|
| `KPI-1` | **证明覆盖率** | `Σ checks(status ∈ {Pass, Waived}) / Σ checks(total)`，按目标数计 | 目标 `≥ 0.98`；`< 0.95` 告警 | `report.json` `summary` | `G-7`、`NFR-6` |
| `KPI-2` | **UNKNOWN 率趋势** | `Σ checks(status = UnknownReviewRequired) / Σ checks(total)`，按周滚动 | 目标 `< 0.01`（`NFR-5`）；连续两周边际上升告警 | `summary.unknown` 时间序列 | `NFR-5`、`G-8` |
| `KPI-3` | **求解延迟 P50/P95/P99** | `checks[].time_ms` 的分位数（仅计 `verdict ∈ {sat, unsat}`） | P99 `< 3000 ms`（`NFR-1`）；P99 `≥ 3000 ms` 告警 | `checks[].time_ms` | `NFR-1`、`G-5` |
| `KPI-4` | **豁免存量与到期预警** | 生效豁免数；`expires` 距今 `≤ 14` 天的豁免数 | 存量非递增；预警数 `> 0` 即提醒 | `waivers[]` | `FR-18`、§7.9 |
| `KPI-5` | **求解器一致性分歧率** | 交叉验证不一致次数 / 已交叉验证次数（`E-XVALIDATE-MISMATCH`） | 目标 `= 0`；任意 `> 0` 即触发后端禁用与上报 | `L2` 交叉验证日志 | `FR-9`、`NFR-5` |
| `KPI-6` | **核最小化收敛度** | `minimized_core_size / raw_core_size` 的均值（仅 `--minimize-core`） | 供 `06 §6.9` 性能调优参考；无硬阈值 | `checks[].conflicting_rules` + `core_minimized` | `06 §6.9` |

> **看板建议**：将 `KPI-1`…`KPI-6` 与 `03 §3.9.3` 的「量级测算表」并联展示——当 `KPI-3`（P99 延迟）与 `KPI-2`（UNKNOWN 率）同时恶化时，根因通常是展开后断言规模 `G` 或域规模 `N` 上升（`03 §3.9.4`），须联合研判而非单独调参。
