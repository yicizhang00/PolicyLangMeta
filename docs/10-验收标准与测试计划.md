### 10.2.4 `AC-4` 不可判定构造静态拦截（`FR-5`；`G-4`；`W8`）

> **修正**：明确退出码 `3`（`COMPILE_ERROR`）与错误码 `E-NONLINEAR`（`09 §9.2 B-15`）；v2.0 未定义编译拦截的退出码。**关键**：拦截必须发生在**编译期**，且**不启动任何求解进程**（`INV-L5`）。

| 项 | 内容 |
|---|---|
| 前置条件 | 单文件仅含一个待测算术构造，其余部分合式 |
| 执行命令 | `policylang check ac4.plm`（纯检查，不求解） |
| 期望 verdict | `none`（编译期未进入求解） |
| 期望退出码 | `3` |
| 期望诊断要点 | `diagnostics[].code = "E-NONLINEAR"`、`severity = "error"`、`fix_template = "FIX-13"`、精确 `span` 指向该算术式；`checks = []` 或 `status = "Error"`；**进程监控证明无求解器子进程被 fork** |

**`AC-4` 多用例表**（`C` = 通过，`X` = 拦截）

| 用例 | DSL 片段 | 构造 | 期望 | 错误码 / 说明 |
|---|---|---|---|---|
| `AC-4-a` | `s.port * s.id > 1000` | `*` **两侧非常量** | `X` | `E-NONLINEAR`（`LinMul` 不成立，`03 §3.4.1`） |
| `AC-4-b` | `2 / s.risk_score > 0.5` | `/` **左侧常量、右侧变量**，且比较右侧为常量 `0.5` | `C`（**修正点**） | 见下方说明：`LinDiv(2, s.risk_score, 1/2) = isConst(2) ∨ isConst(1/2) = ⊤` ⇒ **线性化通过**，保持 `QF_LIA` |
| `AC-4-b1` | `s.risk_score / 2 > 0.5` | `/` 除数**常量** | `C` | 常量除数，直接编码 `(/ … 2)` |
| `AC-4-c` | `2 / s.risk_score > s.threshold` | `/` 左侧常量、**除数**变量，比较右侧**亦为变量** | `X` | `LinDiv` 不成立（两侧皆非常量）⇒ `E-NONLINEAR` |
| `AC-4-d` | `s.a div s.b > 10` | `div` **变量除数** | `X` | `E-NONLINEAR`（floor 除法不可线性化，`命题 3.11.1`） |
| `AC-4-e` | `s.a mod s.b == 0` | `mod` **变量除数** | `X` | `E-NONLINEAR` |
| `AC-4-f` | `2 * s.id > 1000` | `*` **单侧常量** | `C` | `LinMul` 成立（对照组，证明守卫**不过度**拦截） |

> **`AC-4-b` 的设计意图（对照 `09 §9.2 C-5`）**：上游 v2.0 的守卫写作 `!left.is_constant() && !right.is_constant()`，**漏检** `2 / x` 一类「左侧常量、右侧变量」的除法。本框架把线性性拆为**两个独立侧条件**（`03 §3.4.1`）：
> - 乘法侧：`LinMul(a,b) ≜ isConst(a) ∨ isConst(b)`；
> - 除法侧：`div`/`mod` **要求除数恒定**；`/` 若除数非常量则须 `LinDiv(a,b,c) ≜ isConst(b) ∨ isConst(c)` 成立（`TH-4` 线性化）。
>
> 故 `AC-4-b`（`2 / s.risk_score > 0.5`）中**比较右侧为常量**，`LinDiv` 成立，**应线性化通过**；而 `AC-4-c`（比较右侧为变量）**应拦截**。两个用例共同界定守卫的**精确边界**：既不漏检（`AC-4-b1`/`AC-4-c`/`AC-4-d`/`AC-4-e`），也不过检（`AC-4-b`/`AC-4-f`）。

### 10.2.5 `AC-5` 理论路由与并行竞速强杀（`FR-8` `FR-9` `FR-17`；`G-5`）

> **修正**：上游「`10 ms` 内 SIGKILL」**不可测**；本框架改为可测的 **首胜后其余子进程回收 P99 ≤ 50 ms**，并显式依赖 `JoinSet::shutdown().await`（`tokio ≥ 1.40`）与 `kill_on_drop(true)`（`02 §5.2`）。

| 项 | 内容 |
|---|---|
| 前置条件 | 查询含字符串正则交集（`matches_all`，`FR-14`），`T(φ)` 推导为 `QF_SLIA` |
| DSL 输入 | `rule PasswordComplexity: forall s in Services: s.uses_db implies s.db_password matches_all [".*[A-Z].*", ".*[0-9].*"]` |
| 执行命令 | `policylang verify slia.plm --timeout 3000ms --output report.json` |
| 期望 verdict | `sat` 或 `unsat`（确定判定） |
| 期望退出码 | 依 `overall_status` 映射 |
| 期望诊断要点 | `logic_used = "QF_SLIA"`；`attestation.winner_solver ∈ {z3, cvc5}`（**`bitwuzla` 不得出现在池内**）；子进程残留率 = 0 |

**`AC-5` 可测指标：P99 强杀回收 ≤ 50 ms**

| 项 | 规范 |
|---|---|
| 指标 | 从**首胜时刻** `t_w` 到**其余求解器子进程全部消失**的耗时 `Δ = t_done − t_w`，取 200 次独立运行的 **P99** |
| 判定方法（进程树快照） | 在 `t_w` 与 `t_w + 50 ms` 两个时点各采样一次进程树：Linux/macOS `ps -eo pid,ppid,comm,stat`，Windows `Get-CimInstance Win32_Process | Select ProcessId,ParentProcessId,Name`。统计**父进程为 `policylang` 且 `comm ∈ {z3, cvc5, bitwuzla}`** 的存活进程数 |
| 通过条件 | (i) `t_w + 50 ms` 快照中该类进程数 = **0**；(ii) 200 次样本全部满足 (i)（即 P100 ≤ 50 ms ⇒ P99 ≤ 50 ms）；(iii) 无「僵尸（`Z`）或孤儿（`PPID=1`）」进程 |
| 反例判定 | 若任一快照仍存在求解器子进程，或观察到孤儿/僵尸，判 `Fail` 并输出快照差异（`NFR-3`） |
| 池筛选验证 | 以**包装脚本**替换 `z3`/`cvc5`/`bitwuzla` 二进制，在 `argv[0]` 记录被调用者；断言 `QF_SLIA` 任务下 `bitwuzla` **从未被调用**（`FR-8` 的屏蔽规则） |

> **为何改为 P99 且用进程树快照**：`Δ` 依赖调度与内核回收延迟，是**分布**而非确定值；「10 ms 内 SIGKILL」是**瞬时断言**，无法在 CI 中稳定复现。进程树快照给出**可复现、可归档**的判定证据，P99 给出**统计口径**，二者结合使指标可验收（`NFR-3`）。

### 10.4.1 全局基线声明

|---|---|
| 硬件基线（CI） | GitHub Actions `ubuntu-24.04`：4 vCPU / 16 GB RAM / 无 GPU |
| 硬件基线（基准机） | 本地基准机：x86_64 8 核 3.5 GHz / 32 GB RAM / Linux 6.x；`BENCH-` 结果以**基准机**为准，CI 结果仅作**回归对比** |
| 求解器 | 由 `policylang.lock` 锁定（Z3 / CVC5 / Bitwuzla 名称+版本+二进制 SHA-256） |
| 计时口径 | 单次求解耗时取 `checks[].time_ms`；统计前**丢弃预热 20 次**，正式样本量 `N = 200` |
| 统计口径 | P50 / P95 / P99（线性插值分位数）；报告**同时**给出均值与标准差（仅供诊断，不作为门禁） |
| 回归门禁 | 若相对上一基线的 P99 劣化 `> 15%` **且**绝对值超过 `NFR` 阈值 ⇒ 门禁失败 |

| 环节 | 规范 |

## 10.5 故障注入测试（`FIT-1` – `FIT-7`）

> **目标**：验证求解层在**异常环境**下的**确定处置**——绝不静默降级、绝不把异常伪装为判定。每一用例给出注入手段、期望处置与退出码。

| ID | 故障 | 注入手段 | 期望处置 | 期望退出码 |
|---|---|---|---|---|
| `FIT-1` | **求解器崩溃**（非零退出 / SIGSEGV） | 包装脚本：以 `argv` 判定并被调用时 `kill -SEGV $$` 或 `exit 139` | 该后端标记为**当次不可用**；若池内仍有其他后端返回确定判定 ⇒ 采信并记录 `W-*` 提示；若**全部**崩溃 ⇒ `E-SOLVER-MISSING` | `4` |
| `FIT-2` | **求解器挂起**（永不返回、不读 stdin） | 包装脚本 `sleep infinity`（或死锁于读） | 由 `--timeout` 触发全员回收；`JoinSet::shutdown().await` 等待子进程退出；**无残留** | `2`（`UnknownReviewRequired`） |
| `FIT-3` | **超时**（正常求解但超出预算） | `--timeout 1ms` 或构造重语料 | `verdict = unknown`；`status = UnknownReviewRequired`；转人工评审（`07 §7.8`） | `2` |
| `FIT-4` | **返回畸形输出** | 包装脚本输出 `satt`、`(((`、非 SMT-LIB 文本或截断括号 | 响应流解析器（`02 §5.3`）返回 `ParseError::NoVerdict`；该后端判为**无效**；若全池无效 ⇒ `E-INTERNAL` | `4` |
| `FIT-5` | **缺失二进制** | 从 `PATH` 移除 `z3`（或 `--solver-path` 指向不存在文件） | 探测/启动失败 ⇒ `E-SOLVER-MISSING`；**不静默降级**（`00 §0.6`） | `4` |
| `FIT-6` | **版本不符** | 替换为不同版本二进制（`bin_sha256` / `version` 与 `policylang.lock` 不符） | `E-SOLVER-VERSION`；拒绝该后端；**不静默采信** | `4` |
| `FIT-7` | **内存耗尽（OOM）** | 以 `ulimit -v`（Linux）或容器内存限额（如 256 MB）限制子进程 | 子进程被内核杀死/退出非零；判为当次不可用；若全池失败 ⇒ `E-SOLVER-MISSING`；宿主评测内存预算（`NFR-3`）不得被击穿 | `4` |

> **通用断言（对全部 `FIT`）**：① **永不**产生 `Pass`（`INV-L3`）；② 每个用例结束后 `NFR-3` 的**子进程残留率 = 0**（进程树快照校验）；③ 报告落盘成功且 `diagnostics[]` 含对应码；④ 若批量中某目标 `Error`，则 `overall_status` 由合并格升至 `Error`（`00 §0.4.2`）。

### 10.5.1 注入基础设施

| 组件 | 用法 |
|---|---|
| 包装脚本目录 `tests/fault/wrap/` | 每个求解器对应一个可执行包装（`bash` / `pwsh`）；由 `--solver-path` 或临时 `PATH` 注入 |
| 环境变量开关 | `PL_FAULT=crash` / `hang` / `timeout` / `malformed` / `missing` / `version` / `oom`，包装脚本据此改变行为 |
| 版本伪造 | `wrap-*` 对 `--version` 返回伪造串，用于 `FIT-6`（并同步改写 `policylang.lock` 的 `bin_sha256` 以触发校验失败） |
| 资源限制 | Linux `ulimit -v 262144`、`systemd-run --scope -p MemoryMax=256M`；Windows Job Object 内存上限；容器 `--memory=256m` |
| 判定采集 | 每个用例采集：进程树快照（首末各一次）、`report.json`、退出码、`diagnostics[]`；比对 `<同名>.expect.json` |
| 与门禁的关系 | `FIT-*` **不**进入 PR 门禁（避免慢/不稳定），仅在夜间与发布前执行；失败即按 §10.8 分级 |

## 10.6 形式化验证的测试

### 10.6.1 Lean 证明的 CI 检查

| 检查 | 手段 | 通过条件 |
|---|---|---|
| 编译 | `cd lean && lake build`（`12 §12`） | **零错误**、**零告警**（`set_option warningAsError true`） |
| 无 `sorry` | 静态扫描 `lean/PolicylangProof/**/*.lean`，匹配 `sorry`/`admit` | **核心算子**（`Grounder`/`Cidr`/`Regex`/`Division`）文件内 `sorry` 计数 **= 0**；`Encoding.lean` 允许**显式登记**的 `sorry`（附证明计划，`03 §3.15`） |
| 定理存在性 | `#check PolicylangProof.Grounder.preserves_semantics` 等（`TH-1`/`TH-2`/`TH-4`/`TH-5`/`TH-6`） | 全部 `#check` 成功且类型与 `03 §3.15` 索引一致 |
| 公理审计 | `#print axioms <theorem>` | 仅允许 `Classical.choice`/`propext`/`Quot.sound`；**禁止** `sorryAx`（除登记项） |

> **分层要求**（`03 §3.15`）：「**已证**」= 无 `sorry` 的完整证明（`TH-1`/`TH-1-C1`/`TH-1-C2`/`TH-2`/`TH-4`/`TH-5`）；「结构证明 + `sorry` 标注」= `TH-6`（须在 CI 白名单）；「陈述」= `TH-7`（`Encoding.lean` 给出类型正确的陈述 + 证明计划）。CI **按分层**校验，不得把「陈述」误当「已证」。

### 10.6.2 Rust 与 Lean 双侧语义一致性差分测试

> **目标**：证明**实现**（Rust）与**模型**（Lean）对同一构造给出**相同语义**，弥合「证明对象」与「运行对象」的鸿沟。

| 项 | 规范 |
|---|---|
| 差分对象 | ① `ground`（`ALG-1`）的语义保持（`TH-1`）；② `mask`/`net` 与 CIDR 掩码等价（`TH-5`）；③ `τ` 正则转译的语言保持（`TH-6`）；④ `linearize_division` 重写等价性（`TH-4`） |
| 生成器 | `proptest` 生成合式 `φ`、CIDR 字面量、`R_sub` 模式、`(a,b,c)` 有理性三元组；**种子固化**并纳入回归语料库（§10.7） |
| Rust 侧判据 | 对每个样本，`⟦ground(φ)⟧ρ` 由**独立参考求值器**（`ModelEvaluator`，精确算术）计算 |
| Lean 侧判据 | 对同一 `φ` 的 AST 编码，调用 Lean 侧语义函数求值（经 `lean --run` 或提取的可执行模型） |
| 一致性 | 两者取值**逐位相等**；不一致即 `Fail`，最小化反例后登记为缺陷（`S1`/`S2`，§10.8） |
| 样本量 | 每类 ≥ 10⁴ 个样本（夜间）；每提交 ≥ 500 个样本（烟雾） |
| 关联 | `TH-1`、`TH-4`、`TH-5`、`TH-6`；`INV-L2`（单一命名实现） |

## 10.7 回归语料库建设

### 10.7.1 分类与规模

| 类别 | 内容 | 规模目标 | 期望行为 |
|---|---|---|---|
| `C1` **正例**（`positive`） | 合式规范，含三大案例与六类排序覆盖 | ≥ 120 份 `.plm` | `Pass`（或按语义 `Fail`），退出码符合预期 |
| `C2` **负例**（`negative`） | 每类 `E-*` 码至少 2 个最小复现（`W1`–`W12` 全覆盖） | ≥ 60 份 | 对应 `E-*` 码 + 退出码 `3` |
| `C3` **退化语料**（`degenerate`） | `N=1`、`k>N`、`matches_all []`、空载体、`safety_vacuous` | ≥ 30 份 | 恒真/恒假/`E-EMPTY-CARRIER`（`AC-12`） |
| `C4` **求解器故障**（`solver-fault`） | 包装脚本注入（`FIT-1`–`FIT-7`） | ≥ 7 组 | 见 §10.5 |
| `C5` **属性种子**（`prop-seed`） | 固化 `proptest` 种子（§10.6.2） | ≥ 200 个种子 | 差分一致 |
| `C6` **审计快照**（`audit-snapshot`） | 冻结的 `report.json` + 期望 `proof_hash` | ≥ 200 份 | `BENCH-6` 复算一致 |

### 10.7.2 维护流程

| 环节 | 规范 |
|---|---|
| 入库 | 每个缺陷修复（§10.8）**必须**附一个最小复现语料，登记于 `tests/corpus/<类别>/` |
| 命名 | `<类别>-<E码或AC>-<序号>.plm`（如 `negative-E-NONLINEAR-007.plm`） |
| 期望值 | 与语料同目录的 `<同名>.expect.json`：`{ verdict, exit_code, codes[], notes }` |
| 审查 | 语料变更走 PR，须由 QA 与形式化工程师**双审** |
| 冻结 | 发布前语料**冻结**；发布后只增不改（历史可比性，`00 §0.2`） |
| 运行 | 每提交跑 `C1`/`C2`/`C3` 子集；夜间跑全量 + `C4`/`C5`/`C6` |

## 10.8 缺陷分级与准出准则

### 10.8.1 缺陷分级（`S1` – `S4`）

| 级别 | 名称 | 定义 | 典型示例 | 修复时限 | 对发布的阻断 |
|---|---|---|---|---|---|
| `S1` | **致命** | **健全性被破坏**：产生**假证明（unsound PASS）**，或审计哈希不可复算，或数据/证据损坏 | `unknown` 被判为 `Pass`；`Bnd` 不可满足时空核被记 `Pass`（`07 §7.3.3`）；`proof_hash` 复算不一致（`TH-10` 失效） | 立即（热修） | **阻断发布** |
| `S2` | **严重** | **门禁或核心功能失效**：退出码映射错误、跨平台强杀残留、交叉验证漏报、崩溃/挂起、`W1`–`W12` 漏检导致不可判定构造进入求解 | 五分支门禁把 `Error` 判为 `Fail`（`B-16`）；`AC-4` 漏检 `2 / x`（`C-5`）；子进程残留率 `> 0` | 发布前 | **阻断发布** |
| `S3` | **一般** | **诊断/性能不达标**：诊断不精确、反例格式化错误、性能超过 `NFR` 阈值、SARIF 字段缺失 | IPv6 压缩形式不规范；`BENCH-1` P99 `> 3 s`；`KPI-2` UNKNOWN 率超标 | 当前迭代 | 不阻断，但**须登记并评估** |
| `S4` | **轻微** | 文案/格式/日志问题，不影响判定与门禁 | 终端配色、`message` 措辞、帮助文本 | 后续版本 | 不阻断 |

> **升级规则**：`S3` 若涉及**安全红线语义**（`invariant`/`refines`/`safety`），自动升级为 `S2`；`S2` 若同时产生错误判定，自动升级为 `S1`。
