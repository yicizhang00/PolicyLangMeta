## 8.0 阅读指引

**本矩阵解决什么问题**。`01`–`07` 分别定义了目标、需求、设计、数学内核、编码、治理与测试，但它们各自成篇；`08` 的唯一职责是把这些碎片**连成可核验的追溯链**，回答三个评审必答问题：① 每条需求是否都落了地（正向覆盖）；② 每个落地制品是否都源自某条需求（反向无孤儿）；③ 每个缺口是否都有可勾选的闭环判据（缺口闭环）。

**列含义（通用）**。`* ID` 列为该表的追溯主体；`覆盖的 …`列为指向其他 ID 池的引用；「状态」列取三值：

- `完整` —— 该主体的每一条实质主张均有下游制品（Crate / spec / 测试）承接，且承接对象已被 `09` 裁决为「已闭环」；
- `部分` —— 主体的大部分主张已承接，但存在一条或多条主张的承接对象被收窄、改名或尚未落地（表下逐条说明）；
- `待补` —— 主体尚无任何下游承接（本文件当前无此类条目）。

**追溯方向**。

- **正向（需求 → 设计 → 实现 → 测试）**：`G` → `FR`/`NFR` → `AC` → `CR`/`ALG`/`TH`/`IF` → `BENCH`/`FIT`/`AC` 用例。用于回答「这条需求由谁实现、如何验收」。见 §8.1、§8.3、§8.4。
- **反向（测试 → 需求）**：`AC`/`BENCH`/`FIT` → `FR` → `G`。用于回答「这条测试证明了什么、它服务哪个目标」。见 §8.2、§8.3。
- **缺口闭环（缺口 → 补全 → 判据）**：`09` 的缺口 → 补全去向 → 落地制品 → 客观闭环判据。见 §8.5。

**如何用它做评审检查**。

1. **正向扫描**：沿 §8.1 检查每行「实现 Crate」「接口契约」「测试用例」三列是否**均非空**；任一为空即该 `FR` 未闭合。
2. **反向扫描**：沿 §8.2 检查每个 `G` 的「衡量标准」列是否含**至少一个可证伪指标**（可被有限测试断言为真/假）；含 `缺口` 者须回到 `09` 对应条目确认裁决状态。
3. **退出码扫描**：沿 §8.3 检查每个 `AC` 的「期望退出码」是否落在 `00 §0.4.3` 的 `0`–`4` 且与其 `status` 一致（`spec/report.schema.json` 的 `allOf` 已机器化该校验）。
4. **参数扫描**：沿 §8.4 检查每个 `NFR` 是否绑定具体参数（`G_max`/`--timeout`/`--max-inflight`）；未绑定者按 `01 §5` 纪律视为不可验收。
5. **缺口扫描**：沿 §8.5 逐条核对「闭环判据」是否为**可勾选的客观条件**（代码形态、断言数值、采样方法），而非「已处理」这类不可核验表述。
6. **孤儿/悬空扫描**：沿 §8.7 核对每个 ID 池的「持有文档」是否存在，并沿 §8.8 的清单核对「有定义无引用（孤儿）」与「有引用无定义（悬空）」。
