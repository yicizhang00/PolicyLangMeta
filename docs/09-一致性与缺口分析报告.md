# 09 · 一致性与缺口分析报告

> **文档角色**：对上游 `需求文档与开发文档.txt`（v2.0）与本次重构后的 v2.1 文档集做**逐条差异审计**，给出遗漏（Omission）、冲突（Conflict）、不一致（Inconsistency）、缺口（Gap）四类问题的完整清单、严重级裁定、证据定位与补全去向。
>
> **审计对象**：`需求文档与开发文档.txt` v2.0（1475 行，含 `TXT +N` 跨文档引用占位符与多处表格破损）
> **审计基准**：`00`（术语与编号）、`03`（形式化语义内核，冻结）
> **审计日期**：2026-10-14　|　**版本**：v2.1
>
> **审计结论（前置）**：上游 v2.0 的**产品直觉与架构分层是正确的**——「编译期可判定性守卫 + 有界量词展开 + 理论感知多求解器竞速 + 反证法双向诊断」这条技术主线成立且具备原创性。但它**不能直接作为工程立项与核心研发蓝本**：
> - 存在 **18 项数学/形式化缺口（A 类）**，其中 5 项（`A-3`、`A-10`、`A-12`、`A-13`、`A-14`）会让「验证通过」这一结论在某些输入上**不可信**；
> - 存在 **33 项工程/接口缺口（B 类）**，其中 12 项使规格**无实现路径**；
> - 存在 **15 项冲突与不一致（C 类）**，其中 `C-1`、`C-4`、`C-5`、`C-9` 是**同一份文档内两条需求互相矛盾**，无法同时满足；
> - 存在 **23 项治理与流程遗漏（O 类）**，其中 `O-4`、`O-5`、`O-15` 使「治理闭环」这一 G-7 目标缺少落地构件。
>
> 上述 **89 项**已在本文件集的 01–12 中**全部闭环处理**（补全 / 修正 / 显式裁决 / 登记为开放问题 OQ）。剩余 **10 项开放问题（OQ-1 ~ OQ-10）**需立项委员会裁决。

## 9.0 分析方法与统计

### 9.0.1 方法

1. **三层校验**：语法一致（文法 ↔ 示例 ↔ 原语表）→ 语义一致（数学陈述 ↔ 编码 ↔ 实现伪码）→ 工程可行（指标 ↔ 手段 ↔ 验收方法）。
2. **反例构造**：对每条断言尝试构造一个**使该断言失败**的具体输入（而非仅做通道检查）。这是发现 `C-5`（`2/x` 漏检）与 `A-3`（组合爆炸）的关键手段。
3. **可证伪性检查**：每条 NFR/AC 必须绑定可测参数与判定方法；未绑定者记为缺口（`C-8`、`C-15`）。
4. **占位符与破损还原**：逐单元格核对 `TXT +N` 占位符与破损表格，做内容归属，确认**无内容丢失**（`§9.7`）。

## 9.6 影响评估与结论

### 9.6.1 若不补全即立项的后果推演

| 缺口 | 直接后果 | 严重性 |
|---|---|---|
| `A-3`（无展开预算） | 首批真实用例（域规模 ≥ 30）即触发编译超时或 OOM，团队会误判为「框架性能不行」而非「模型写大了」 | 项目在 `M-1` 内即受挫 |
| `B-7`（`uses_*` 未置位） | 理论路由恒为 `ALL`，所有求解器都被调度 ⇒ 含字符串的查询被路由到 Bitwuzla 并直接报错 ⇒ `FR-8` 与 `AC-5` 自始不通过 | 阶段二阻塞 |
| `C-1`（增量 vs 强杀） | 实现者必在二者间二选一，无论选哪边都会破坏另一条需求，评审时被判定为「需求不闭合」 | 设计评审不通过 |
| `C-9`（10 ms 强杀） | `AC-5` 作为可测量的验收项，会在每次测试中出现随机失败（flaky），消耗大量排查成本后被发现是**指标本身不可实现** | 质量成本浪费 |
| `A-12`（除法 `unspecified`） | 风控案例中的比率策略通过验证，但真值因除零未指定而可能不同 ⇒ **假证明**。这是形式化验证工具最不可接受的失效模式 | 产品信誉 |
| `A-13`（最小核） | 用户按「最小冲突核」报告删除规则，可能删掉必需规则 ⇒ 引入新缺陷 | 反向伤害用户 |

### 9.6.3 结论

1. **上游 v2.0 的技术主线成立**，不需要推翻架构，只需**补全与修正**。
2. **15 项 P0 缺口必须在 `M-1` 前闭环**；本文档集已全部给出裁决与补全，可在 `M-0`（立项评审）时一次性确认。
3. **10 项开放问题（`OQ-1` ~ `OQ-10`）需委员会裁决**，其中 `OQ-5`（是否保留 `--allow-nonlinear`）与 `OQ-9`（Lean 证明是否为硬门禁）影响 `G-4`/`G-8` 的目标表述，**建议在立项评审当日决议**。
4. 补全后，本文档集（`01`–`12` + `spec/` + `lean/` + `examples/`）**具备作为工程立项与核心研发蓝本的条件**：需求可追溯（`08`）、数学有定理（`03`）、编码有规范（`06`）、验证有测试（`10`）、风险有登记（`11`）、形式化有机械证明路径（`12`）。
